Ele analisa os imports do seu projeto e ajusta as dependências do módulo.

import "github.com/gin-gonic/gin"

go mod tidy

Quando você inicializa uma struct com campos normais (valores), Go atribui o valor padrão de cada tipo. Quando você usa ponteiros, o valor padrão de qualquer ponteiro em Go é sempre nil.


type EstruturaValor struct {
	Ativo  bool
	Nome   string
	Idade  int
}

type EstruturaPonteiro struct {
	Ativo  *bool
	Nome   *string
	Idade  *int
}

func main() {
	v := EstruturaValor{}
	fmt.Printf("Valor -> Ativo: %t, Nome: %q, Idade: %d\n", v.Ativo, v.Nome, v.Idade)
	// Saída: Ativo: false, Nome: "", Idade: 0

	p := EstruturaPonteiro{}
	fmt.Printf("Ponteiro -> Ativo: %v, Nome: %v, Idade: %v\n", p.Ativo, p.Nome, p.Idade)
	// Saída: Ativo: <nil>, Nome: <nil>, Idade: <nil>
}

Dica para ponteiros -> Precisa alterar dados? Entao ponteiro. Quer ler dados? Então nao use ponteiro. Nao usando ponteiro vc passa a copia e depois 
da execução ele perde todos os dados alterados.

Interface -> Criei o PaymentProcessor, qualquer struct que tenha um metodo Pay(amount float64) error exatamente assim ira implementar a interface
PaymentProcessor.

repare que embaixo fiz processPayment -> ela diz que eu posso passar um metodo de pagamento e a quantidade não preciso especificamente ser de um tipo.
isso implementa PaymentProcessor? → então consigo chamar Pay()

Mas se eu quiser posso fazer 

PixPayment{}.Pay(100) que ai nao preciso chamar a funcao processPayment que espera alguem que implemente a função Pay.

Posso chamar PixPayment{}.Pay(100) diretamente, porque estou trabalhando com o tipo concreto PixPayment. Já processPayment recebe um PaymentProcessor, então ele aceita qualquer tipo que implemente Pay(amount float64) error.


type PaymentProcessor interface {
	Pay(amount float64) error
}

type PixPayment struct{}
type CreditCardPayment struct{}

func (p PixPayment) Pay(amount float64) error {
	fmt.Println("Processing PIX payment:", amount)
	return nil
}

func (c CreditCardPayment) Pay(amount float64) error {
	fmt.Println("Processing Credit Card payment:", amount)
	return nil
}

func processPayment(payment PaymentProcessor, amount float64) error {
	return payment.Pay(amount)
}

processPayment(PixPayment{}, 100)
processPayment(CreditCardPayment{}, 200)

//SUPONHA QUE TENHA O METODO Show()
type PaymentProcessor interface {
	Pay(amount float64) error
	Show()
}

E você faz:
type PixPayment struct{}

func (p PixPayment) Pay(amount float64) error {
	fmt.Println("PIX:", amount)
	return nil
}

Nesse momento, PixPayment não implementa PaymentProcessor, porque falta: Show()

Se tentar executar: processPayment(PixPayment{}, 100) o Go vai reclamar em compilação, porque PixPayment não satisfaz a interface.

Você teria que fazer:

func (p PixPayment) Show() {
	fmt.Println("Showing PIX payment")
}

O que é Context?

Simplificando bastante:

context.Context carrega informações sobre o ciclo de vida de uma operação.

Principalmente:
	cancelamento
	timeout/deadline
	valores associados à operação

Para backend, os dois primeiros são os mais importantes inicialmente.

func main() {
	ctx := context.Background()

	fmt.Println(ctx)
}

context.Background() cria um contexto raiz.
Pense nele como:

"Comece uma nova operação."

Não pense: "context.Context é uma coisa que eu preciso passar porque Go exige."

Pense: "Essa operação pertence a uma requisição/operação maior e preciso carregar o ciclo de vida dela pelas camadas."

ESTUDANDO CONTEXTO.


O "select" funciona como uma corrida de canais: o que entregar o dado primeiro ganha, executa o seu respectivo bloco de código e encerra a estrutura.


select {
	case X:
		// contexto cancelado
		return ...
	case Y:
		// operação terminou
		return ...
	}

Codigo:

	func doSomething(ctx context.Context) error {
		select {
		case <-ctx.Done():
			fmt.Println("Operação foi cancelada.")
			return ctx.Err()
		case <-time.After(5 * time.Second):
			fmt.Println("Operação Terminou.")
			return ctx.Err()
		}
	}

	ctx, cancel := context.WithTimeout(
			context.Background(),
			2*time.Second,
		)

		defer cancel()

		doSomething(ctx)


WithTimeout diz -> "Depois de 2 segundos, minha operação deve ser cancelada."

Se deixar o context com 2 seg de timeout o select vai esperar o 1° evento que bater, que será no ctx.Done() e imprimir "Operação foi cancelada."
Se colocar o tempo de 2*time.Second para 8 seg, ele vai cair no case <-time.After(5 * time.Second).

<-ctx.Done()

Done() retorna um channel.

ctx.Done()
    ↓
"canal que será sinalizado quando o contexto for cancelado"

E o: <-

significa que estamos esperando receber algo desse canal.

Por isso funciona perfeitamente dentro do select.

ESTUDANDO goroutine + channel

O que é uma goroutine?

Uma goroutine permite executar uma função de forma concorrente.

exp: go doSomething()

você diz:
"Execute essa função concorrentemente; não preciso esperar aqui para continuar."
main
 │
 ├── go doSomething()
 │       ↓
 │    executando
 │
 └── continua imediatamente

Um channel permite que goroutines se comuniquem.
ch := make(chan string)

Exemplo de codigo:
	func sayHello(ch chan string) {
		time.Sleep(2 * time.Second)

		ch <- "Hello"
	}

	func main() {
		ch := make(chan string)

		go sayHello(ch)

		message := <-ch

		fmt.Println(message)
	}

	//O make é uma função embutida (built-in) usada exclusivamente para inicializar e alocar memória para tipos de dados especiais: fatias (slices), mapas (maps) e canais (channels).
    //Se você apenas declarar um canal ou um mapa sem o make, ele nascerá com o valor nil (nulo), o que causará problemas no seu programa:
	//go sayHello(ch) => você está dizendo ao Go para executar sayHello em uma goroutine concorrente, enquanto a goroutine principal pode continuar.
main
 │
 ├── cria channel
 │
 ├── inicia goroutine
 │       │
 │       └── espera 2s
 │
 ├── espera <-ch
 │
 │       2s
 │       ↓
 │    ch <- "Hello"
 │
 └── recebe "Hello"

Quando você faz:
message := <-ch

A execução bloqueia até existir algo para receber.
Ou seja:
<-ch
 │
 ├── tem mensagem? → continua
 │
 └── não tem? → espera

Isso é fundamental para entender channels.

Cuidado: concorrência ≠ paralelismo

Concorrência:
lidar com várias tarefas em andamento.

Paralelismo:
executar tarefas literalmente ao mesmo tempo em diferentes recursos de CPU.

Go trabalha muito bem com concorrência, e o runtime decide como executar as goroutines.

Channel com buffer:
ch := make(chan string, 1) => O 1 significa que o channel consegue armazenar 1 valor antes de precisar de um receiver.

• canal <- valor :Envia o valor para dentro do canal (é o caso de ch <- "hello").
• variavel := <-canal: Recebe (lê) um valor que está vindo de dentro do canal.

ch := make(chan string)

    go func() {
        ch <- "hello"
    }()

    fmt.Println(<-ch)

Neste exemplo:
	ch := make(chan string, 1)

	ch <- "A"
	ch <- "B"

	fmt.Println(<-ch)

Irá guardar o VALOR "A" e depois dará DEADLOCK. Pois como tem o buffer "1" make(chan string, 1) só poderá guardar 1 valor.
Lembre-se Para channel funcionar ou tu precisa do buffer ou de uma função com goroutine.

ch <- "A"
O buffer está vazio. "A" é armazenado.
Buffer: ["A"]

ch <- "B"
O buffer já está cheio. Como ninguém recebeu "A", o envio de "B" fica bloqueado.
Bloqueado — não chega ao fmt.Println.

fmt.Println(<-ch)
Essa linha nunca é executada, porque o envio anterior bloqueou a goroutine principal.


SOLUÇÃO:
	ch := make(chan string, 1)

	ch <- "hello"
	fmt.Println(<-ch)  //AQUI ESTAMOS LIBERANDO O CHANNEL LIMPANDO SEU VALOR PARA RECEBER OUTRO VALOR.

	ch <- "hello 2"
	fmt.Println(<-ch)

	OUTROS EXEMPLOS:

	ch := make(chan string, 2)

	ch <- "hello"

	ch <- "hello 2"
	fmt.Println(<-ch)

	SAIDA:
		hello
		
	-----------------------------------------------------
	ch := make(chan string, 2)

	ch <- "hello"

	ch <- "hello 2"
	fmt.Println(<-ch)
	fmt.Println(<-ch)

	SAIDA:
		hello
		hello 2

	-----------------------------------------------------
	ch := make(chan string, 1)

	ch <- "hello"

	ch <- "hello 2"
	fmt.Println(<-ch)
	

	SAIDA: DEADLOCK! DA ERRO.

O que é um Handler?

Um handler é uma função responsável por tratar uma requisição HTTP.
No Go, usando a biblioteca padrão net/http, podemos criar um handler assim:

	func healthHandler(w http.ResponseWriter, r *http.Request) {
		// Trata a requisição
	}


Entenda os dois parâmetros:
- w http.ResponseWriter: permite escrever a resposta que será enviada ao cliente.
- r *http.Request: contém os dados da requisição recebida, como método HTTP, URL, headers e body.


Estrutura de pastas:
	Router: decide qual handler recebe a requisição.
	Handler: interpreta HTTP e monta a resposta.
	Service: executa as regras de negócio.
	Repository: consulta ou persiste dados.


Exemplo de transformação de dados:

1) Marshal vs Unmarshal (Focado em Memória: []byte)

Você usa essa dupla quando o dado já está totalmente carregado na memória do computador na forma de um array de bytes ([]byte) ou string

1.1) Marshal ->	Empacota -> Transforma uma Struct do Go em uma**[]byte (JSON)**. -> Salvar configurações na memória ou gerar um texto JSON para log.

1.2) Unmarshal -> Desempacota -> Transforma uma []byte (JSON) de volta em uma Struct do Go. -> Você já leu o arquivo inteiro ou recebeu uma string de texto JSON pura e quer ler os campos.

Exemplo de codigo:
	// MARSHAL: Struct -> []byte (JSON)
	dadosBytes, _ := json.Marshal(p1) 

	// UNMARSHAL: []byte (JSON) -> Struct
	var p2 Pessoa
	json.Unmarshal(dadosBytes, &p2) 

2. Encode vs Decode (Focado em Fluxos: io.Writer e io.Reader)

Você usa essa dupla quando o dado está vindo ou indo para um fluxo contínuo (Stream). O Go lê ou escreve o dado aos poucos, diretamente da rede ou do disco, sem precisar carregar tudo na memória de uma vez

2.1) Encode -> Codifica e envia -> Pega uma Struct do Go, converte em JSON e escreve direto no fluxo (io.Writer). -> Responder a uma API enviando dados ao cliente (w http.ResponseWriter).

2.2) Decode -> Lê e decodifica -> Lê direto do fluxo (io.Reader), converte o JSON e popula a Struct. -> Ler os dados que o usuário enviou no corpo de uma requisição HTTP (r.Body).

Exemplo de codigo:
	// DECODE: Lê do fluxo (ex: requisição HTTP) e joga na struct
	json.NewDecoder(r.Body).Decode(&p1) 

	// ENCODE: Pega a struct e escreve direto no fluxo (ex: resposta HTTP)
	json.NewEncoder(w).Encode(p1) 


TESTES para execução via terminal:

1) get -> curl -i http://localhost:8080/welcome

2) post -> curl -i -X POST http://localhost:8080/welcome

3) post com dados -> curl.exe -i -X POST http://localhost:8080/services -H "Content-Type: application/json" -d "{\"name\":\"Desenvolvimento de sites\",\"price\":1500}"

No qual:
-i: exibe o status HTTP e os headers da resposta.
-X POST: define o método HTTP como POST.
-H "Content-Type: application/json": informa que o corpo da requisição é JSON.
-d '...': envia os dados no corpo da requisição.

4) post invalido -> curl.exe -i -X POST http://localhost:8080/services -H "Content-Type: application/json" -d "{\"name\":\"Desenvolvimento de sites\",\"price\":}"

5) delete -> curl.exe -i -X DELETE http://localhost:8080/services/123

6) patch -> curl.exe -i -X PATCH http://localhost:8080/services/123 -H "Content-Type: application/json" -d "{\"price\":1800}"
